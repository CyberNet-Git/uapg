# ADR-006: Отказ от двойного хранения событий

## Статус

Предложено — 2026-10-01. Требует решения по срокам; реализация не начата.

## Контекст

Событие сейчас хранится в двух местах:

- `events_history` — полный состав полей в `event_data JSONB` (каждое значение
  как `"base64:"` + двоичное представление `ua.Variant`). Это **единственное**
  место, откуда можно восстановить событие для `HistoryRead`.
- `events_ts` + `evt_<тип>` — слой поиска: отметка времени, источник, тип и
  отдельные колонки под поля, по которым фильтруют.

Режим `v2` не отменяет первую таблицу: `uapg_save_event_v2` всё равно пишет в
`events_history`, а чтение склеивает результат через `events_ts.legacy_row_id`.
То есть «v1» — это не старый путь, который остался включённым по
недосмотру, а хранилище самих событий.

Из этого следует, что «отключить v1» нельзя одним флагом: сначала событиям нужно
место в слое поиска.

### Чего не хватает, чтобы собрать событие из слоя поиска

- Колонки типизированных таблиц объявлены `TEXT`, и значения приводятся к строке:
  `LocalizedText` теряет локаль, `NodeId`, числа, булевы и массивы становятся
  своим строковым видом, байты декодируются с заменой символов. Обратно в
  `ua.Variant` нужного типа это не восстановить.
- Базовые поля (`Time`, `EventType`, `SourceNode`, `ReceiveTime`, `LocalTime`)
  колонками не заводятся. Первые три восстанавливаются из `events_ts` и
  справочников, последние два теряются.
- Поля с именами, непригодными для идентификатора (`/2:CustomField`), в колонки
  не попадают вовсе.
- Состав колонок зависит от настройки установки (`EventsV2Config`): в одной
  инсталляции в поиске участвуют два поля, в другой десять.

### Состояние на сегодня

В проде включён v1: `HISTORY_STORAGE_VERSION` по умолчанию `v1`
(`opc-vibro-iot-server/src/config/config.py`), в окружении не переопределён.
`events_ts` пуст, типизированных таблиц нет, перенос ни разу не запускался.

### Смежный дефект, который надо устранить раньше

Ретенция двух хранилищ не согласована: `events_history` живёт по
`global_retention_period` (в проде 30 дней), а `events_ts` — по зашитым в
миграции 004 365 дням. Как только включается v2, появляется окно, в котором
строка поиска уже есть, а её полезной нагрузки больше нет: `HistoryRead` отдаёт
меньше событий, чем нашёл фильтр, и молча. Это надо исправить до включения v2 и
независимо от этого ADR — политику `events_ts` следует брать из того же
`global_retention_period`.

## Решение

Перенести полезную нагрузку в слой поиска и отказаться от `events_history`:

1. Колонка `event_data JSONB` в `events_ts` (миграция 006). Формат значений не
   меняется — тот же `"base64:"`, что и сейчас, поэтому кодек и уже накопленные
   данные совместимы.
2. Запись — одной строкой в `events_ts` вместо двух таблиц;
   `uapg_save_event_v2` упрощается и больше не возвращает `legacy_row_id`.
3. Чтение — из `events_ts` напрямую, с запасным путём на `events_history`, пока
   в ней остаются события.
4. `events_history` удаляется отдельной административной командой, не
   автоматически.

Гранулярность и дедупликация не меняются: у обеих таблиц уникальность по
`(source_id, event_timestamp)`, то есть одно событие источника на отметку
времени.

### Почему не массовый перенос старых строк

Очевидный ход — `UPDATE events_ts SET event_data = ...` по всей истории — плохо
сочетается с политикой сжатия: чанки `events_ts` старше 7 дней сжаты, а
обновление сжатого чанка требует его распаковки. На боевой базе это
перезапись всей гипертаблицы.

Дешевле выждать: с момента релиза, где запись идёт в `events_ts`, новые события
уже полные, а старые уходят по ретенции. Когда в `events_history` не остаётся
строк старше момента переключения, таблицу можно удалять без переноса вообще.
При ретенции 30 дней это месяц, при 365 — год; установки, которые не хотят
ждать, могут скопировать нагрузку принудительно (с распаковкой чанков) — это
допустимый, но необязательный путь.

## План

**Шаг 1. Включить v2 и довести перенос до конца.** Согласовать ретенцию
`events_ts` с `global_retention_period`, выставить `HISTORY_STORAGE_VERSION=v2`,
прогнать `run_events_backfill()` до нуля отставания. Изменений в uapg, кроме
ретенции, не требуется.

**Шаг 2 (3.1). Нагрузка в `events_ts`.** Миграция 006: колонка `event_data`,
новая версия `uapg_save_event_v2` без записи в `events_history`, новая версия
`uapg_read_events_v2` с выдачей нагрузки. Чтение берёт её из `events_ts`, а при
отсутствии — из `events_history` по `legacy_row_id`. Признак `partial` и машинерия
переноса остаются.

**Шаг 3 (3.2). Отказ.** Когда критерии ниже выполнены: убрать запасной путь
чтения, режим `legacy` и различие двух классов (остаётся один
`HistoryTimescale`, `HistoryTimescaleV2` — псевдоним), выключить перенос,
добавить команду удаления `events_history` и обновить контракт.

## Критерии готовности к шагу 3

Проверяется на каждой инсталляции:

1. Все установки работают на v2 и обновлены до релиза со шагом 2.
2. Перенос завершён: `run_events_backfill()` возвращает `backfill_lag_rows = 0`,
   узел `EventsBackfillComplete` равен `true`.
3. В устаревшем хранилище нет событий, записанных до переключения, — то есть все
   оставшиеся строки имеют нагрузку в `events_ts`:

   ```sql
   SELECT count(*) FROM events_history eh
   WHERE NOT EXISTS (
       SELECT 1 FROM events_ts et
       WHERE et.legacy_row_id = eh.id AND et.event_data IS NOT NULL
   );
   -- должно быть 0
   ```

4. Запасной путь чтения не срабатывает: счётчик обращений к `events_history`
   при чтении (ввести на шаге 2) держится на нуле не меньше недели под реальной
   нагрузкой.
5. Снята резервная копия базы, и принято, что откат на 3.0 и 0.2.x после
   удаления таблицы невозможен.

## Риски и ограничения

- **Необратимость.** После шага 3 старые версии uapg с этой базой не работают.
  Отсюда требование резервной копии и отдельной команды удаления.
- **Сжатие и нагрузка.** `event_data` попадёт в сжатые чанки `events_ts`.
  Чтение отдельных событий из сжатого чанка дороже, чем из обычной таблицы;
  перед шагом 2 стоит замерить `HistoryRead` по старому диапазону и при
  необходимости поднять порог сжатия.
- **Размер строки.** Нагрузка переезжает в гипертаблицу с пространственным
  партиционированием по источнику; распределение по чанкам изменится.
- **Контракт.** Схема перестанет совпадать со снимком 0.2.15. На шаге 2 нужно
  зафиксировать новый эталон от 3.x и оставить старый как историю, иначе список
  осознанных отступлений потеряет смысл.
- **Публичный API.** `run_events_backfill()` и метрики `events_v2.*` лучше
  сохранить как заглушки на один релиз, чтобы не ломать вызовы в
  opc-vibro-iot-server.

## Последствия

- Одна запись на событие вместо двух таблиц плюс типизированная строка.
- Чтение без соединения по `legacy_row_id`.
- Исчезают перенос, его курсоры, проба готовности, индекс `idx_events_history_id`
  и признак `partial` — вместе с заметной частью кода и настроек.
- Режимы `legacy`/`dual`/`v2` теряют смысл: остаётся одно хранение.

## Отложено

- Восстановление события целиком из типизированных колонок (без `event_data`).
  Потребовало бы типизированных колонок с настоящими типами и места для полей,
  не ставших колонками; выгода сомнительна.
- Агрегаты `ReadProcessed` — отдельный вопрос, см. ADR-003.
