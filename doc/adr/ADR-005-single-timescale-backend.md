# ADR-005: Единственный бэкенд на TimescaleDB (uapg 3.0)

## Статус

Принято — 2026-09-18.

## Контекст

К версии 0.2.15 в пакете было три способа хранить историю и две схемы
администрирования:

- `HistoryPgSQL` — PostgreSQL без TimescaleDB, таблица на каждый узел; в проде
  не использовался;
- `HistoryTimescale` — основной бэкенд, один класс на 4736 строк, в котором
  жили пул и реконнект, метрики, кэши, буфер записи, DDL, сериализация и
  публикация узлов OPC UA; SQL — f-строками;
- `HistoryTimescaleV2(HistoryTimescale)` — надстройка с типизированным поиском
  событий, связанная с базовым классом через `super()` и ссылки на объект пула
  (отсюда ADR-004);
- `DatabaseManager` и CLI — с собственной схемой, не совпадающей с той, что
  создаёт бэкенд.

Тестов против базы не было: все тесты работали на моках, а `pytest.ini` из-за
неверного имени секции не применялся вовсе.

## Решение

1. Один бэкенд — `HistoryTimescale`. `HistoryTimescaleV2` остаётся тонким
   подклассом, который отличается только разрешением режима событий по
   умолчанию: так вели себя два класса раньше, и так их выбирает
   opc-vibro-iot-server.
2. Реализация переписана по слоям: `core` (настройки, соединение, надзор,
   метрики, буфер), `codec` (формат записи), `storage` (схема, переменные,
   события, поиск), `opcua` (семантика чтения, фильтр, узлы). Весь SQL — в
   файлах `sql/`.
3. `Database` — единственная точка доступа к PostgreSQL и не отдаёт пул наружу.
   Класс ошибок «ссылка на закрытый пул» из ADR-004 становится невозможным.
4. Публичный API и схема БД сохраняются. Это не декларация, а проверка:
   контракт 0.2.15 заморожен машинно (подписи и ключи метрик вместе с типами
   значений, снимок схемы, побайтовый формат записи), и тесты сравнивают с ним
   текущий код. Каждое отступление перечислено в
   `tests/contract/divergences.py` с причиной.
5. `HistoryPgSQL`, `DatabaseManager`, CLI, старая реализация слоя событий и
   неиспользуемые миграции 101/102 удалены.
6. Интеграционные тесты идут против одноразовой TimescaleDB, включая сквозной
   тест через настоящие сервер и клиент asyncua, на asyncua 1.1.8 и 2.x.

## Последствия

- Существующие базы работают без миграции.
- `opc-vibro-iot-server` не требует изменений; пути `uapg.v2.events_config` и
  `uapg.v2.storage_mode` сохранены реэкспортами.
- `opc-vibroiot-db` импортирует `uapg.db_manager` и перестанет работать с 0.3;
  код админ-утилиты нужно перенести туда из 0.2.15 (коммит `18df1cf`).
- `events_history` остаётся источником полного состава события: слой поиска
  хранит только поля для фильтрации. Отказ от неё потребовал бы восстанавливать
  событие из типизированных колонок — отдельное решение.
- Для ReadProcessed/ReadAtTime/HistoryUpdate ограничение остаётся на стороне
  asyncua (ADR-003).

## Найдено при переписывании

Ошибки 0.2.15, обнаруженные тестами против живой базы и исправленные в 0.3:

- значение с кодом качества Bad не записывалось и уносило всю пачку
  (`INTEGER` не вмещает 32 бита без знака);
- стандартный клиент получал пустую историю событий в режимах `dual`/`v2`:
  числовой NodeId типа события принимался за `event_type_id` в базе;
- после таймаута флаша backend в PostgreSQL продолжал выполнять запрос и
  держать блокировки;
- advisory lock для DDL брался и снимался на разных соединениях пула, ключ
  зависел от `PYTHONHASHSEED`, а проверка колонок шла на каждом событии;
- перенос событий в типизированные таблицы застревал на первой порции;
- любая ошибка SQL пересоздавала весь пул соединений;
- синхронная запись при полной очереди могла ждать бесконечно;
- чтение истории падало на asyncua 2.x (`DataValue(StatusCode_=…)`).
