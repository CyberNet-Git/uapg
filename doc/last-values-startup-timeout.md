# Таймаут `read_last_values` на старте: разбор и план правок

Статус: **разбор завершён, код не правился.** Документ написан для передачи в сессию,
которая работает локально и имеет доступ к стенду.

Исходная жалоба — на старте сервера (`rts@192.168.1.250`, uapg 0.2.25) в логе повторяется:

```
[E] [history_timescale.py:1898] [_run_db_operation] PostgreSQL fetch timed out after 120.0 seconds (layer=query)
[E] [history_timescale.py:2295] [_fetch] Fetch timed out, will reconnect without retrying: ...
[E] [history_timescale.py:4677] [read_last_values] Failed to read last values: ...
```

Это **одно** событие, а не три: `_run_db_operation` срабатывает по `db_query_timeout_sec`
(120 с) → `_fetch` вызывает `_force_reconnect` и пересоздаёт пул → `read_last_values`
гасит исключение широким `except` и возвращает `None` **на все** узлы, а не только на
медленные.

## Что показал стенд

```sql
SELECT (SELECT count(*) FROM history.variable_metadata)                 AS variables,
       (SELECT count(*) FROM history.variables_last_value)              AS cached,
       (SELECT count(*) FROM history.variables_last_value WHERE is_seed) AS seeds;
--  variables | cached | seeds
--     169031 | 159339 |     0

SELECT count(*) FROM timescaledb_information.chunks
 WHERE hypertable_name = 'variables_history';
--  5340
```

**9692 переменные не имеют строки в `variables_last_value`.** Именно по ним и только по
ним `read_last_values` уходит в фоллбэк по истории — одним запросом с `CROSS JOIN LATERAL`
сразу на все 9692.

Индексы на `variables_history` на этой БД все шесть на месте, включая
`idx_variables_history_vid_ts_desc_covering`. **Это важно: регрессии 0.2.25 здесь нет.**
Старт лишние индексы не удаляет, а `uapg indexes apply --drop-obsolete` на стенде не
запускался.

## Почему «просто взять последнее значение» дорого

Метка времени есть, индекс `(variable_id, sourcetimestamp DESC)` есть. На **обычной**
таблице `WHERE variable_id = X ORDER BY sourcetimestamp DESC LIMIT 1` — один спуск по
B-дереву, десятки микросекунд (измерено на стенде 0.2.25: 0.083 мс,
`Index Scan Backward`).

Дорого становится потому, что `variables_history` — **гипертаблица**. Физически это не
одна таблица, а множество дочерних чанков, и **у каждого чанка свой отдельный индекс**;
глобального индекса по всей гипертаблице не существует. Поэтому «самая свежая строка
переменной X» не находится одним спуском: планировщик обязан достать верхнюю строку из
индекса **каждого** неотсечённого чанка и слить их. `LIMIT 1` останавливает слияние, но
не отменяет проб — по одной на чанк.

Предиката по времени в этом запросе нет вообще (`history_lookback=None` по умолчанию),
поэтому не отсекается ни один чанк. А для переменной, у которой истории **нет совсем**,
доказательство пустоты требует пройти все чанки и вернуть ноль строк — самый дорогой из
возможных исходов.

### Арифметика

5340 чанков / 128 space-партиций ≈ 42 временных чанка. Равенство
`variable_id = v.variable_id` отсекает до одной space-партиции, то есть на переменную
остаётся ~42 чанка. 9692 × 42 ≈ **400 тысяч проб индекса в одном запросе**. При любой
разумной цене пробы это минуты — ровно то, что видно на 120 с.

### И это повторяется на каждом старте

Самозалечивающий upsert после фоллбэка пишет в `variables_last_value` **только найденные**
строки. Переменная без истории строки не даёт → в кэш ничего не попадает → следующий старт
платит ту же цену заново. Бесконечно.

**Это и есть настоящий дефект: не таймаут, а то, что дорогой путь не может сам себя
закрыть.**

## Инструменты TimescaleDB для last-point: что подходит, а что нет

Оговорка: документацию сверить не удалось (`docs.tigerdata.com` закрыт сетевой политикой
окружения; окружение `uapg` с доступом к ней создано, но перенести в него уже запущенную
облачную сессию нельзя). Ниже помечено, что следует из устройства гипертаблиц и от версии
не зависит, а что надо проверить на установке.

**`last(value, time)` / `first(value, time)`** — агрегаты, а не поиск по индексу: они
сворачивают все строки, попавшие под `WHERE`. Для одной серии `ORDER BY ts DESC LIMIT 1`
по индексу быстрее, и именно так uapg уже и делает. То есть `last()` был бы **хуже**
текущего кода. (Уверенность высокая по сути; точную формулировку в документации не
сверял.)

**SkipScan** — оптимизация под `SELECT DISTINCT col` и `DISTINCT ON (col) ... ORDER BY
col, ts DESC` с индексом, у которого `col` ведущая. По форме это наш случай, и
CHANGELOG 0.2.7 показывает, что `DISTINCT ON` когда-то использовался и был заменён именно
из-за деградации «на hypertable с большим числом чанков». Довод, не зависящий ни от версии,
ни от того, включится ли SkipScan: он сокращает работу *внутри* одного индекса, пропуская
повторы ведущего ключа, но **не сокращает число чанков**. Самая свежая строка переменной
может лежать в любом из 42, обойти нужно все. Fan-out остаётся.

**Непрерывные агрегаты** — прецедент в репозитории есть (`uapg_events_hourly`, миграция
`004_events_v2_timescale.sql`), но здесь не подходит: агрегат на 169 тысяч серий × бакеты
даст десятки миллионов строк; внутри него всё равно придётся искать последний непустой
бакет на переменную — тот же last-point на другой таблице; и у агрегата есть лаг
обновления, а нужно текущее значение. Допустимость `last()` внутри continuous aggregate
версионно-зависима — проверять на установке.

**`enable_chunk_skipping`** (min/max метаданные по неврéменной колонке) — не поможет, и это
тоже структурный довод: все 169 тысяч переменных пишутся непрерывно, поэтому в каждом чанке
присутствует почти весь диапазон `variable_id`, min/max на чанк ≈ [1, 169031], отсекать
нечего. Возможность полезна для колонок, коррелирующих со временем.

**Что TimescaleDB действительно даёт — отсечение чанков по времени.** Единственный
работающий здесь рычаг, и он уже есть в API как `history_lookback`. Предикат
`sourcetimestamp >= now() - interval` сокращает ~42 чанка на переменную до одного-двух,
то есть в 20–40 раз: вместо 400 тысяч проб около 20 тысяч. Для живой переменной строка в
последнем чанке есть по определению, а для мёртвой запрос вернёт пусто **быстро** вместо
пусто медленно.

**Вывод.** Готового инструмента под «последнее значение для каждой из 170 тысяч серий» у
TimescaleDB нет; рекомендуемый для такого масштаба приём — отдельная небольшая таблица
последних значений. В uapg она уже есть: `variables_last_value`, **обычная** таблица
(гипертаблицы только `variables_history` и `events_history`) с `variable_id` в первичном
ключе. Проблема не в отсутствии инструмента, а в том, что эта таблица не поддерживается
полной.

## Корень: инвариант объявлен, но не исполняется

DDL-комментарий у `variables_last_value` утверждает: «для каждой зарегистрированной
переменной здесь есть строка (см. `seed_last_values`)». **Код этого не обеспечивает.**
Проверено: `new_historized_node` (`history_timescale.py:3489`) и `new_historized_nodes`
(`:3527`) пишут только в `variable_metadata`; строку в `variables_last_value` создаёт лишь
`seed_last_values`, которую должен позвать вызывающий код. Отсюда расхождение
169031 / 159339.

`read_last_values` внутри uapg не вызывается ни разу (проверено по всему `src/`) — это
серверный код делает массовое восстановление последних значений на старте.

## План правок

### 1. Строка кэша создаётся при регистрации переменной

`new_historized_node` и `new_historized_nodes` после записи в `variable_metadata` сеют
строку в `variables_last_value`. **Переиспользовать существующий `seed_last_values`**
(`:4688`), не писать новый SQL: он уже делает ровно нужное и идемпотентен
(`ON CONFLICT (variable_id) DO NOTHING`).

Проверено по коду, что он корректно принимает `dv=None`:

- `variant = getattr(dv, 'Value', None) if dv is not None else None` → `ua.Variant(None)`,
  то есть Null-вариант, `varianttype = 0`;
- метки времени → `now`;
- `status_from_datavalue(None)` → `BadWaitingForInitialData` (0.2.24 как раз сделала этот
  код записываемым — до неё Bad-коды в `INTEGER` не влезали вовсе);
- `is_seed = TRUE`.

То есть `seed_last_values([(node_id, None)])` для только что зарегистрированных узлов —
всё, что нужно; для `new_historized_nodes` — одним батчем на список.

### 2. Разовый ремонт существующих — одним set-based запросом

В `_create_metadata_tables`, рядом с уже живущими там идемпотентными `ALTER TABLE`:

```sql
INSERT INTO "{schema}".variables_last_value
    (variable_id, sourcetimestamp, servertimestamp, statuscode, varianttype, variantbinary, is_seed)
SELECT m.variable_id, NOW(), NOW(), $1, $2, $3, TRUE
FROM "{schema}".variable_metadata m
LEFT JOIN "{schema}".variables_last_value lv ON lv.variable_id = m.variable_id
WHERE lv.variable_id IS NULL
ON CONFLICT (variable_id) DO NOTHING
```

Параметры: `$1` — закодированный `BadWaitingForInitialData` (`uapg.status_code.encode_status`),
`$2` — `0` (`VariantType.Null`), `$3` — `variant_to_binary(ua.Variant(None))`. Считать
теми же функциями, что и `seed_last_values`, **не хардкодить байты**.

Запрос **не трогает гипертаблицу вообще** — только две обычные таблицы по `variable_id`.
На 9692 строках это миллисекунды. Идемпотентен: на следующем старте анти-джойн вернёт
ноль строк. Залогировать на INFO число посеянных строк и выставить метрику, иначе
расхождение инвентаря снова будет невидимым.

### 3. `is_seed=TRUE` — обещание уточнить, а не подмена значения

Риск: часть из 9692 может иметь реальную историю, просто потеряв строку кэша. Посеяв им
Null/Bad, мы скрыли бы настоящее значение. Ровно для этого и существует флаг `is_seed`:
`backfill_last_values` (`:4762`) заменяет сиды реальными последними значениями из истории
**порциями** (`chunk_size=100`), с таймаутом на чанк и опциональным `history_lookback`,
забирая соединение из пула напрямую и передавая `timeout=` в `conn.fetch` — то есть минуя
`_run_db_operation` и не вызывая `_force_reconnect`. Он написан именно под этот случай.

Последовательность: сид закрывает дорогой путь немедленно, `backfill_last_values` в фоне
доводит сиды до реальных значений, серверный код применяет их через `on_chunk_restored`.

### 4. Дефолтное окно поиска в истории

Раз единственный работающий рычаг — отсечение чанков по времени, не оставлять его
выключенным по умолчанию. Параметр конструктора
`history_last_values_lookback: Optional[timedelta] = timedelta(days=7)` задаёт значение
`history_lookback` по умолчанию и для фоллбэка в `read_last_values`, и для
`backfill_last_values`. Явный аргумент вызова главнее; `None` — как сейчас, вся история.
Сигнатуры не меняются, но ловушка «по умолчанию сканируем все 5340 чанков» уходит.

### 5. Фоллбэк в `read_last_values` — ограничить, он больше не несущий

Раз инвариант исполняется, фоллбэк остаётся только для повреждённой БД. Ограничить, чтобы
он физически не мог повторить этот отказ: пачками по `chunk_size`, с таймаутом на пачку и
общим бюджетом, тем же приёмом, что в `backfill_last_values`. На таймауте — отдать
собранное, один WARNING с подсказкой, инкремент счётчика. Частичный результат лучше
нынешнего `None` на все 169 тысяч узлов. **Дефолт `allow_history_fallback` не менять** —
это публичный API, и кто-то на фоллбэк полагается.

### 6. Видимость

Счётчики `last_values_*` живут только в `get_cache_stats()` (`:1146`) и не попадают в
`get_performance_metrics()`, а значит и в диагностические узлы OPC UA. Добавить секцию
`last_values`: попадания/промахи, число фоллбэков, число посеянных строк и новый
`last_values_fallback_timeouts`. Без этого проблема диагностируется только чтением лога —
как и получилось.

### 7. Индекс, который на новой БД уже не создастся

На стенде он есть, но на любой БД, поднятой 0.2.25 с нуля, его не будет, и там этот же
старт упрётся в то же место. Вернуть в `CORE_INDEX_SPECS` индекс
`(variable_id, sourcetimestamp DESC)` — **без** `INCLUDE`: порядок ключа нужен этому
LATERAL (CHANGELOG 0.2.7 называет его прямо), а payload
`INCLUDE (statuscode, varianttype, servertimestamp)` действительно мёртв, потому что
запрос тянет `variantbinary`, которого в payload нет, и index-only быть не может.

Имя новое (`idx_variables_vid_ts_desc`), так как `build_plan` сравнивает только имена и
старый широкий индекс навсегда считался бы `present`. Прежний covering остаётся в
`OBSOLETE_INDEX_SPECS`.

**Это ошибка 0.2.25, и её стоит назвать прямо:** удаляя covering, довод был про
бесполезность `INCLUDE` — и он верен, — но `DESC`-порядок ключа нужен был именно этому
LATERAL, и это было упущено. На стенде последствий нет только потому, что старт индексы не
удаляет.

## Что можно сделать на хосте сразу, без релиза

**Закрыть дорогой путь одним запросом** (то же, что п.2; `-2144206848` — это
`BadWaitingForInitialData` в знаковом представлении из 0.2.24, значение сверено на живой
БД в том релизе):

```sql
INSERT INTO history.variables_last_value
    (variable_id, sourcetimestamp, servertimestamp, statuscode, varianttype, variantbinary, is_seed)
SELECT m.variable_id, NOW(), NOW(), -2144206848, 0, '\x00'::bytea, TRUE
FROM history.variable_metadata m
LEFT JOIN history.variables_last_value lv ON lv.variable_id = m.variable_id
WHERE lv.variable_id IS NULL
ON CONFLICT (variable_id) DO NOTHING;
```

Оговорка: `'\x00'` — кодирование Null-варианта по OPC UA Part 6 (байт маски 0, тела нет).
Python-ом это не проверялось. Сверить на одной строке, что `read_last_value` по такой
переменной возвращает Null-значение со статусом `BadWaitingForInitialData` и не падает;
если нет — сеять через `seed_last_values`, он соберёт байты сам.

**И в вызове на старте** до релиза — любой из двух вариантов:

```python
# либо не ходить в историю вовсе
values = await history.read_last_values(nodes, allow_history_fallback=False)
# либо ходить, но с отсечением чанков по времени
values = await history.read_last_values(nodes, history_lookback=timedelta(days=7))
```

Поднимать `db_query_timeout_sec` — **не** решение: запрос всё равно съест минуты и порвёт
пул.

## Что проверить при реализации

Отказ воспроизводится только на гипертаблице: дорогим запрос делает fan-out по чанкам, на
чистом PostgreSQL этого эффекта нет. Разбор выше опирается на чтение кода, лог и цифры со
стенда — **прямого замера нет**, его надо сделать.

1. Стенд с TimescaleDB, похожий по форме (не по масштабу): гипертаблица с недельными
   чанками, 128 space-партиций, несколько тысяч переменных, у части — ни строки в истории,
   ни строки в `variables_last_value`.
2. **Воспроизвести отказ на текущем коде**: один `read_last_values` по всем переменным
   упирается в таймаут и возвращает `None` на все узлы.
3. `EXPLAIN (ANALYZE, BUFFERS)` на LATERAL: показать **число фактически просканированных
   чанков** на переменную без истории, и что с `history_lookback` оно падает до
   одного-двух. Там же подтвердить, что отсечение работает для параметризованного
   `variable_id` внутри LATERAL (runtime chunk exclusion) — единственное в разборе про
   TimescaleDB, что не проверено.
4. После п.1–2: тот же вызов не обращается к гипертаблице вовсе
   (`last_values_history_fallbacks == 0`) и укладывается в единицы миллисекунд.
5. Регистрация новой переменной сразу даёт строку со статусом `BadWaitingForInitialData` и
   Null-значением; повторная регистрация идемпотентна.
6. `backfill_last_values` заменяет сиды реальными значениями и не вызывает
   `_force_reconnect` (метрика `db.reconnects_*` до и после).
7. Таймаут одной пачки ограниченного фоллбэка не роняет весь вызов: частичный результат,
   счётчик таймаутов растёт.
8. Полный `pytest` (на 0.2.25 — 258 passed) и мутации: снять сид при регистрации — тест на
   инвариант обязан покраснеть; снять бюджет фоллбэка — тест на частичный результат обязан
   покраснеть.

**Поведенческое изменение, которое надо согласовать:** сейчас для этих 9692 переменных
`read_last_values` отдаёт `None`; после правки — `DataValue` с Null и статусом
`BadWaitingForInitialData`. По спецификации это корректнее, чем «ничего», но код
восстановления адресного пространства должен такое принимать.

## Полезные запросы для диагностики

```sql
-- расхождение инвентаря: разница и есть переменные, по которым идёт LATERAL
SELECT (SELECT count(*) FROM history.variable_metadata)      AS variables,
       (SELECT count(*) FROM history.variables_last_value)   AS cached;

-- множитель стоимости
SELECT count(*) FROM timescaledb_information.chunks WHERE hypertable_name='variables_history';

-- версия расширения: от неё зависят SkipScan и chunk skipping
SELECT extversion FROM pg_extension WHERE extname = 'timescaledb';

-- какие индексы реально используются
SELECT indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
  FROM pg_stat_all_indexes
 WHERE schemaname='history' AND relname='variables_history' ORDER BY idx_scan;
```
